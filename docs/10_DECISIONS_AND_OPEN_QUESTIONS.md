## 2. 已采纳决策说明

### D-001：产品类别和承诺边界

**决策**：FakeLive 面向想独自直播、练习表达、玩游戏或看视频时获得即时回应的人。它提供可控的 AI 直播间氛围，但不提供医疗治疗，也不替代人与人的关系。

**理由**：用户真正追求的是“像百大 UP 主一样能和一片弹幕互动”的体验，而不是搭建直播平台基础设施。

**后果**：所有 AI 人数都必须写作“模拟在线”；默认不做真实平台登录、真实观众混流或公开房间。

### D-003：云端 step-explore 取代本地模型主链路

**决策**：第一版通过 `https://api.stepfun.com/v1/messages` 调用内部 `step-explore`，采用 Anthropic Messages 请求风格。

**理由**：用户明确指定该内部多模态模型，并表示 token 与成本不是当前约束。

**后果**：必须在开播前说明所选画面和主播转写会发送到 StepFun。只可承诺本地不主动持久化原始媒体；在条款确认前，不承诺云端不留存。

### D-004：32 个独立人格，而不是一次批量伪装

**决策**：产品目标是 32 个会话内持久身份。每个人格有自己的提示、短期历史、活跃倾向、沉默判断和请求标识，最终形态允许每人格独立调用。

**理由**：人格之间的反应差异、连续性和偶发复读是体验本身，而不是 UI 装饰。

**后果**：一个请求返回 32 句只能用于 Fake 或故障演示，不能作为最终语义。与此同时，“32 个身份存在”也不等于“32 路真实请求已稳定同时运行”，后者必须实测。

### D-005：导演只调度，不代写

**决策**：人群导演的输出限制为 `intensity`、`eventKey`、`targetActivePersonas`、`burstDuration`、`confidence` 等结构化字段。

**理由**：让导演生成台词会把人格声音重新合并成一个中心模型，也难以判断某句弹幕属于谁。

**后果**：导演失败时回到基础热闹度；不能伪造重大事件，也不能阻断现有正常人格。

### D-006：桌面级弹幕层

**决策**：主输出使用独立透明无边框 Electron 窗口，直播态置顶、无背景、无控件、鼠标穿透。控制台和恢复界面是独立窗口。

**理由**：核心体验是弹幕真正飘过游戏或视频，而不是旁边多一个聊天窗。

**后果**：必须验证 Windows 原生点击穿透、DPI、捕获自身排除、全局快捷键、托盘恢复和独立解锁窗。网页内 locator 点击不构成证明。

### D-007：语音是完整体验核心，但与画面链路解耦

**决策**：主播语音由麦克风采集并先转写成带时间戳文本，再进入观察快照。`step-explore` 是否原生接收音频不作假设。

**理由**：用户明确要求 AI 能回应主播说话，而目前给出的接口手册只确认多模态模型与 Messages 接口，没有确认音频块。

**后果**：使用 `SpeechProvider` 隔离本地/云 ASR。仅画面模式可以用于容错，但不能通过语音互动验收。

### D-008：冷场策略

**决策**：用户界面使用正向的“冷场策略”：

- `自然冷场`：没有值得回应的内容时，所有人格都可以沉默。
- `持续热闹`：人格可以根据主播背景、游戏主题、近期对话和常见梗做环境型发言，但不能假装刚发生了不存在的击杀。

**理由**：真实直播间既有安静时刻，也有闲聊与烂梗。用户需要控制氛围，而不是一个含义模糊的“允许空结果”开关。

### D-009：短输出与时效性

**决策**：人格每次输出 `silent` 或 1 至 2 条弹幕。弹幕必须带 `observationId`、创建时间、显示期限、模式和优先级。

**理由**：长文本破坏弹幕可读性；迟到的“开了？”或“可惜”会制造错误语境。

**后果**：任何过期输出直接丢弃，不为了节省 token 而在晚到时继续展示。

### D-010：全局限流与反压

**决策**：所有人格共享一个 RateController。每人格最多一个在途调用和一个“最新待处理观察”；新快照覆盖旧等待项。

**理由**：32 个客户端各自指数退避会在 429 后同步重试，形成放大流量。

**后果**：统一处理 `Retry-After`、抖动退避、并发下调、熔断和半开探测。持续热闹任务先于事件反应被暂停。

### D-011：内容安全底线

**决策**：可以让用户选择“友好、嘴硬、毒舌、串子”等风格，但以下内容不允许被关闭：威胁、受保护群体仇恨、自伤鼓励、公开隐私与凭据、涉及未成年人的性内容。

**理由**：风格化吐槽是产品价值的一部分，但安全红线不能由人格设定绕过。

**后果**：Prompt 约束不是唯一防线；模型输出还需结构校验、内容过滤和最终屏蔽词过滤。

P0 实现固定为 Zod 边界、Unicode 规范化、版本化 `hard-deny-v1` 高风险规则、用户词表和频率上限；过滤器错误时直接丢弃候选。公开发布前再评估独立分类器或审核服务，不能把黑客松规则包宣传为全语言覆盖。

### D-016：StepAudio 2.5 实时 ASR

**决策**：第一版使用 StepFun [StepAudio 2.5 ASR](https://platform.stepfun.com/docs/zh/guides/models/stepaudio-2.5-asr)。直播主链路采用 `stepaudio-2.5-asr-stream` 与 `wss://api.stepfun.com/v1/realtime/asr/stream`，通过 `Authorization: Bearer $STEPFUN_API_KEY` 鉴权。客户端持续发送音频分片，默认试用服务端 VAD；`stepaudio-2.5-asr` 的一次性 SSE 作为分段转写 Spike/回退候选，不冒充双向实时流。

**后果**：本地只承担麦克风采集、重采样、音量计和有界分块，不运行本地 ASR 模型；默认启用 StepAudio `server_vad`，减少本地 ONNX/CPU 占用。只有 `completed.transcript` 或已经稳定的最终字词能进入观察上下文；累计型 `delta.text` 必须整体替换，不能追加。实时帧编码、会话时长、心跳、限流和错误恢复仍属于真实探针项。

### D-017：完整观察窗口，关键帧请求

**决策**：客户端按约 1 fps 保留最近 10 或 20 秒的有界帧窗口，但每个导演或人格请求默认只发送由去重、变化检测和事件时间选出的 2 至 4 张关键帧，并附时间戳与转写摘要。

**后果**：不把 10/20 张图片无条件复制给每个人格。Gate 0 仍要验证图片块结构、尺寸和延迟；后续只有在实测证明有价值且可承受时，才增加关键帧上限或提供完整窗口实验模式。

### D-018：并发以实测 N 为准

**决策**：32 个逻辑人格与独立调用语义是产品目标，但“32 路同时成功”不是黑客松的硬性通过条件。测试按 `1 -> 4 -> 8 -> 16 -> 32` 逐级执行，在出现持续 429、超时或体验延迟前停止扩压，记录当前构建与账户的最高稳定并发 N。

**后果**：演示至少跑通 4 个真实独立人格以证明多人格闭环；其余身份可以轮换调度。所有界面、报告和口头说明统一写“内置 32 个身份，真实并发已验证到 N”，不得把目标值写成实测值。

### D-027：原型使用自有 StepFun 密钥

**决策**：黑客松原型由开发者填写自己的 StepFun 密钥。按当前官方合同，同一 `STEPFUN_API_KEY` 分别用于 step-explore 的 `/v1/messages` 和 StepAudio 的 `/v1/realtime/asr/stream`；密钥只发往 `api.stepfun.com`，不把共享产品密钥内嵌进安装包，也不在原型阶段建设账号、计量、额度和反滥用网关。

**后果**：控制台只配置一次密钥，但分别显示 Step-explore 与 StepAudio 的“可用/无权限/连接失败”健康状态，不能回显原文。Main 可把同一值通过两个独立、限定 origin 的注入通道交给对应 Adapter。未来若面向普通用户提供免填密钥的统一额度，必须新增服务端代理与独立 ADR，不能沿用桌面直连拓扑。

### D-028：默认直接调侃，不默认羞辱

**决策**：首次开播默认使用 `热闹游戏房`，调侃强度为“直接”，允许问号、反串、`开了？`和针对操作的短吐槽；`允许粗口`与`直接嘲笑失误`默认关闭，因此不默认出现 `FW`、持续贬低或强烈羞辱。

**后果**：A2/A3 人格和词汇只有在用户主动开启相应设置后才能参与。重置配置后回到 A1；安全红线、连续负面上限和立即降级/停用始终不可关闭。

## 3. 仍待确认

Q-001、Q-002、Q-003 已在 2026-07-23 收敛为 D-016、D-017、D-018。ASR 供应商与模型也已收敛为 StepAudio 2.5；实现前仍需探针实时帧格式、心跳、会话长度、限流和取消语义。

### Q-005：扬声器选择服务什么功能？

**推荐默认**：首版只用于测试音和未来语音播报的输出目标，不采集系统声音。若黑客松没有任何输出音效，界面可以保留设备能力但不把扬声器选择列为开播门槛。

### Q-008：紧急解锁快捷键采用什么组合？

**推荐默认**：提供一个不易误触的固定默认组合，并在首次校准中要求实际按下验证。此处待确认的只有默认键位；全局快捷键、托盘和独立恢复窗三条路径全部通过，才允许进入完全穿透态。

## 4. Gate 0：真实 API 能力探针

以下问题在探针前保持未知，禁止由“Anthropic 兼容”自行推断：

1. 图片 content block 的确切结构、支持 MIME、单图与总请求大小。
2. `system` 支持字符串还是 content blocks。
3. SSE 事件名称、顺序、usage 和 error 的实际结构。
4. `AbortController` 后服务端释放速度，以及断流能否安全重试。
5. `temperature`、`top_p`、`stop_sequences` 等参数是否支持。
6. 429 是否包含 `Retry-After`，实际并发/RPM 上限和恢复曲线。
7. 输入窗口、输出上限、首 token 和完整响应延迟。
8. StepFun 对截图、转写、Prompt 和日志的保存与训练政策。

Gate 0 的退出证据必须包含脱敏请求/响应夹具、SSE 时间线、错误矩阵和并发阶梯结果；不能只留一句“curl 200”。

## 5. 已明确后移

- 接入真实 B 站、虎牙或其他直播间弹幕。
- 用户账号、公开房间、云同步和社交关系。
- 通用第三方插件 SDK、沙箱、市场和版本兼容体系。
- 专用手环协议；若设备表现为标准 Windows 麦克风则无需专用适配。
- 图片/表情弹幕、任意路径、对象识别避让、人脸蒙版、历史回放。
- 多显示器同时输出、独占全屏覆盖和跨 GPU/HDR 的完整兼容承诺。
- 长期人格记忆、跨会话用户画像和云端原始媒体历史。
