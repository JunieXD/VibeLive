# 产品说明

> 状态：Working Draft
>
> 目标平台：Windows、macOS
>
> 本文只描述产品行为。可替换的技术实现见 [ARCHITECTURE.md](./ARCHITECTURE.md)。

## 1. 产品概述

AI 虚拟直播间让用户在没有真实观众的情况下获得类似直播间的实时互动体验。

用户选择一个屏幕、窗口或应用作为画面来源，并选择一个麦克风。应用持续理解近期画面、用户发送的文字和用户刚说过的话，让一群有稳定身份的 AI 观众通过弹幕与用户交流。观众体验按“模式 > 模式内人格 > 成长梗库”组织，同一时间只激活一个模式。

这里的“直播”是一种本地体验：

- 不向公网推流。
- 不创建可供真人进入的房间。
- 不接入真实观众账号、礼物或在线人数。
- 不把 AI 观众包装成真人。

## 2. 用户与场景

### 2.1 目标用户

- 想练习直播表达，但暂时没有观众的用户。
- 玩游戏、看视频或演示内容时，希望获得即时回应的用户。
- 想测试节目效果、解说节奏或互动方式的内容创作者。

### 2.2 核心场景

- 用户玩游戏时，AI 根据近期画面和用户解说生成反应。
- 用户播放或讲解内容时，AI 提问、评论或接话。
- 用户进行普通桌面演示时，AI 对当前内容提供观众视角的反馈。

产品不应绑定某一款游戏。具体游戏可以作为测试样例，但不能成为底层产品前提。

## 3. 核心价值

### 3.1 相关

弹幕需要与近期屏幕内容、用户刚说的话或用户发送的文字有关。缺乏足够上下文时，可以保持安静，不能捏造刚刚发生的事情。

### 3.2 及时

过期反应会破坏直播感。系统需要为观察和弹幕保留时间信息，并丢弃已经失去语境的结果。

具体延迟目标由原型测量后决定，当前不预设固定秒数。

### 3.3 像观众

每个观众实例都有自己的名字、人格、偏好、表达方式和会话内状态。同一个观众在一次 Session 中需要保持连续，不能只是每次随机换一种语气。所有观众同时访问同一直播间的公开上下文和共享长期记忆，但会因人格和实例微变体产生不同反应。

观众之间可以有不同意见、不同关注点和不同活跃程度。它们不必对每件事都表态，也不应在每次生成时全体同时出现。

### 3.4 可控

用户始终知道系统正在采集什么、模型是否工作，并能立即暂停、清屏或停止。

### 3.5 有关系和连续性

用户可以通过文字弹幕或语音直接和观众说话。观众能够识别用户是在对房间、某个观众或近期话题作出回应，并在后续互动中延续已经形成的称呼、偏好、观点和关系。

这种连续性必须来自明确的观众状态和记忆，不能只依赖一次请求中的临时 Prompt。产品仍需清楚标注这些角色是 AI，拟人化不等于冒充真人。

## 4. 核心流程

### 4.1 开始前

用户能够：

1. 选择画面来源。
2. 选择麦克风并确认输入正常。
3. 配置或选择外部模型连接。
4. 选择一个观众模式，并查看该模式内参与的 AI 观众。
5. 查看将发送给外部模型的数据类型。
6. 调整基础弹幕偏好。
7. 开始一次虚拟直播会话。

画面来源、弹幕显示目标和麦克风是不同概念，界面不能将它们混为一个设置。

### 4.2 进行中

应用持续完成以下闭环：

1. 从用户选定的来源取得近期画面。
2. 采集用户选定的麦克风，通过用户启用的 ASR Provider 转成文本。
3. 接收用户主动发送的文字弹幕，并立即作为用户消息进入房间。
4. 将有效的近期画面、用户文字、语音文本和房间对话组成观察上下文。
5. 为参与的 AI 观众加载各自的人格和会话内状态，以及当前相关的直播间共享记忆。
6. 通过已配置的 Model Provider 请求弹幕候选。
7. 对候选的身份归属、结构、时效、重复和内容进行检查。
8. 在桌面覆盖层中显示通过检查的弹幕，并将公开互动写回房间状态。

直播中需要展示简洁的运行状态，至少能区分：

- 画面是否正在采集。
- 麦克风是否有输入。
- ASR Provider 是否正常。
- 外部模型是否可用。
- 弹幕生成是否暂停或发生错误。
- 当前有哪些 AI 观众参与。

### 4.3 控制命令

| 命令 | 用户可观察语义 |
| --- | --- |
| 暂停 | 暂停新的观察和生成，不继续积压待显示内容 |
| 恢复 | 从新的上下文继续，不补发暂停前已经过期的弹幕 |
| 清屏 | 立即移除屏幕上和待显示队列中的弹幕 |
| 隐藏 | 暂时不显示弹幕；是否继续生成必须在界面中明确说明 |
| 停止 | 结束会话，停止采集、ASR、模型请求和弹幕输出 |

“隐藏”和“暂停”不能做成含义相同但名称不同的按钮。

## 5. MVP 范围

当前仓库已经具备 Electron/React 桌面端、FastAPI/SQLite 基础设施、StepFun ASR、OpenAI-compatible Provider 和 protocol v1 实时链路。本轮待交付的是把前端模式/人格工作区与后端统一为本文定义的 Viewer runtime/protocol v2；现有 v1 链路或前端 demo 不能作为下列 v2 能力已经实现的证据。

### 5.1 必须具备

- Electron 桌面应用能够在 Windows 和 macOS 启动。
- FastAPI 后端能够随应用启动、报告健康状态并正常退出。
- 用户能够选择并采集一个画面来源。
- 用户能够选择一个麦克风并看到输入状态。
- 麦克风语音能够通过已配置的 ASR Provider 形成带时间信息的文本。
- 用户能够发送自己的文字弹幕，并在房间中区分用户消息与 AI 弹幕。
- 系统能够组合近期画面、用户文字、近期语音文本和公开房间对话。
- 至少一个用户配置的外部多模态模型能够生成相关弹幕。
- 房间包含多个稳定的逻辑观众；每个观众拥有独立身份、人格、偏好和会话状态。
- 当前产品保留 32 个基础 PersonaTemplate 作为内置素材库，并提供 6 个观众模式；模板数量与 Session 中 1 到 32 个 ViewerInstance 的数量没有一一对应关系。
- 内置模式可以复制为自定义模式；模式内人格覆盖互相隔离，编辑一个模式不能改写其他模式的同名人格。
- 用户可以通过完整人格编辑器修改人格字段，并以带格式版本的 `personality.md` 表示可迁移的人格定义。
- 当前模式拥有独立的成长梗库；自动入库可撤销，梗条目可持久化，并可随时间衰减后归档。
- 用户通过文字或语音发起交流后，观众能够针对内容作出有身份连续性的回应。
- 每条 AI 弹幕都能追溯到一个明确的观众 ID，不能由无身份的“系统观众”直接显示。
- 同一 ViewerInstance 在 Session 中保持自己的短期状态；所有 Viewer 共享 Room 工作记忆和跨 Session 的长期记忆。
- 每个被 Director 选中的 ViewerInstance 对应一次独立模型调用，并可返回一条弹幕或合法 silence。
- 人格、模式和模型配置能够通过带 revision、hash 和 epoch 的原子热更新应用到当前 Session。
- 系统提供机器可读 Debug API、结构化 trace、headless harness 和确定性 replay。
- 模型接入不直接耦合业务层，替换 Provider 不需要改动采集和弹幕模块。
- 弹幕能够显示在不阻碍用户操作的桌面覆盖层中。
- 暂停、清屏、恢复和停止具有清楚且可验证的行为。
- 网络、模型或 ASR 失败时，控制界面和停止操作仍然可用。
- 界面明确标注 AI 观众和外部模型数据发送状态。

### 5.2 暂不要求

- 向直播平台推流或连接真实直播间。
- 真人账号、礼物、关注、付费和公开房间。
- 每次 Session 都使用全部 32 个内置 PersonaTemplate，或每轮都让全部 ViewerInstance 参与。
- 把多个 ViewerInstance 合并为一次模型调用；首版保持一实例一独立请求。
- 多显示器同时覆盖。
- 系统音频、摄像头或面部表情理解。
- 云同步或用户账号。
- 插件市场和第三方脚本执行环境。
- 支持所有外部模型协议。

第一版只承诺 OpenAI-compatible 多模态接入；“兼容”表示采用该类请求协议，不表示所有第三方服务支持相同的图像、结构化输出或流式能力。

## 6. 配置范围

第一版可以提供以下配置，但具体控件和默认值需要结合原型调整：

- 画面来源和弹幕目标。
- 麦克风、StepFun ASR 连接状态和凭据。
- 外部模型 Provider、服务地址、模型名称和凭据。
- 模式选择、模式复制和模式内人格名单。
- 完整人格编辑、版本化 `personality.md` 和模式内覆盖管理。
- 当前模式的成长梗库、自动入库撤销、停用和归档管理。
- 弹幕字号、速度、透明度、显示区域和密度。
- 观众氛围、语言风格和内容强度。
- 用户屏蔽词和是否允许安静。

高级参数不应成为首次启动的阻碍。系统应提供可工作的默认配置，同时允许用户进入高级设置连接自己的模型。

## 7. AI 观众行为

### 7.1 房间事件

系统将所有公开互动归一化为带时间和来源的房间事件：

- `screen_observation`：从近期画面中选择的一个或多个帧。
- `user_text`：用户主动发送的文字弹幕。
- `user_voice`：ASR Provider 产生的用户最终语音文本。
- `audience_barrage`：已经公开显示的 AI 观众弹幕。
- `system_event`：开始、暂停、恢复或主题变化等必要状态。

文字和语音在进入房间后具有相同的对话地位，但保留不同的来源标记。系统不保证每次请求都包含相同数量的帧或历史事件，也不要求把整个观察窗口发送给模型。

### 7.2 模式层级

产品当前提供 32 个内置 PersonaTemplate 和 6 个内置模式。32 个模板是可扩展素材库，不代表固定房间人数。模式通过 `viewer_count`、人格权重、模式内覆盖和成长梗库决定本次 Session 的 ViewerInstance 池；`6657` 与其他模式一样由用户主动选择，任何时刻最多只有一个激活模式。

内置基础人格是可复用起点，不要求每轮全部参与。模式对人格的名称、角色、颜色、特征、表达方式、行为约束和启用状态所做的覆盖只在该模式生效。内置模式的调整可以重置到基线，用户也可以复制后形成长期自定义模式；任何编辑都不能意外改写其他模式或内置基础人格。

完整人格编辑器应覆盖产品定义的全部人格字段。人格可以序列化为 `personality.md`，文档格式必须携带明确版本，使导入、导出和后续迁移能够被校验；格式不兼容时必须报告错误，不能静默丢字段。

本地工作区不存在时可以使用默认配置；已有工作区无法读取或不兼容时必须进入受保护状态，禁止自动保存或关闭时覆盖。用户可以重试加载，或在保留拒绝副本后显式重置。应用升级时以内置人格稳定 ID 合并当前基线，不能因为内置文案更新而丢失自定义人格、模式覆盖或成长梗。

### 7.3 观众实体

每个 AI 观众至少具有：

- 当前 Session 内稳定且不可复用的 `viewer_instance_id`。
- 显示名称和可选头像。
- PersonaTemplate ID、revision、核心人格特征和价值倾向。
- 确定性实例微变体。
- 喜好、话题、互动方式、语言习惯和回复长度倾向。
- 会话内的短期私有状态，例如最近已公开发言、直接互动、注意点、临时情绪和冷却。

核心人格不能被一次模型输出随意改写。ViewerInstance 的短期状态可以演化；公开事件进入所有 Viewer 共享的 Room 记忆，并必须带来源、revision 和本地规则。

### 7.4 成长梗库

梗可以来自用户文字、用户语音、近期真实事件或 AI 之间已经发生的互动。导演对这些上下文作出判断后，可以输出独立的 `MemeCandidate`；通过本地校验的候选自动进入当时的激活模式，不得串入其他模式。

自动入库需要支持撤销。已保留的梗需要持久化，并根据后续使用和时间变化衰减；失去活跃度的条目进入归档，而不是继续无限参与生成。当前桌面策略在启动时归档超过 30 天未使用、累计使用少于 3 次且未置顶的条目；归档可恢复，这组初始参数可在取得真实使用数据后调整。

导演同时保留用于发言调度的 `CrowdDecision` 输出。`MemeCandidate` 与 `CrowdDecision` 是两类独立合同：导演候选不能直接成为弹幕，也不能绕过观众身份、时效和内容检查进入 Overlay。已入库的梗只有在后续由明确观众生成合法弹幕时，才可能显示给用户。

### 7.5 输出

输出是零条或多条弹幕候选。每条候选至少关联 `viewer_instance_id`、Persona ID、文本、reaction type 和 evidence refs；渲染所需的样式、优先级、版本和过期信息由本地系统补充。

模型原始输出不能未经校验直接显示。

### 7.6 拟人化要求

为了形成真实观众感，生成结果需要满足：

- 不同观众关注不同信息，不只是更换口头禅。
- 观众能够回应用户，也可以在合适时回应其他观众。
- 观众可以沉默、误解、改变心情或坚持观点，但不能无故违背核心人格。
- 观众知道的内容来自当前房间事件、Room 共享记忆和明确配置，不能假装知道未提供的现实信息。
- 相同场景不要求所有观众给出相同立场。
- 用户点名某个观众时，系统能够把这次交流关联到该身份。

输入被合并为 ObservationWave。FastAPI 计算本轮硬预算，Director 选择准确 ViewerInstance；每个被选实例进行一次独立请求，同一波使用冻结上下文，AI 弹幕不能直接递归触发新波。具体时间窗口、阈值和预算数字仍通过 telemetry 调整。

### 7.7 记忆边界

- RoomWorkingMemory 用于维持当前 Session 的公开对话连续性，所有 Viewer 下一波可见。
- RoomLongTermMemory 只保存从公开互动中提炼出的必要事实、共同经历和 room lore，不保存原始音频或连续画面。
- 长期记忆绑定 `room_id`，跨 Session 和模式共享；Persona 只影响关注和表达，不形成私有事实库。
- 用户能够查看、修改、撤销、删除或重置 Room 长期记忆。
- 长期记忆在波次后异步提取，不阻塞弹幕；用户事实必须有非 AI 证据。

## 8. 隐私与安全基线

- 用户必须明确选择采集来源和麦克风。
- 界面应说明哪些数据保留在本地，哪些数据会发送给 ASR 或模型 Provider。
- 原始麦克风音频只发送给用户明确启用的 ASR Provider；第一版的目标服务是 StepFun。
- 弹幕生成模型只接收最终语音文本，不接收原始麦克风音频。
- 屏幕帧、用户文字、转写文本和必要的房间上下文只发送到用户明确配置并启用的 Provider。
- 默认不持久保存原始音频和连续屏幕帧。
- 人格模板、Room 共享长期记忆和模式成长梗保存在本地，并提供查看、修改和删除能力。
- 日志不得记录模型凭据、原始音频、完整屏幕图像或未经处理的长段转写。
- 停止会话后应释放媒体设备、取消在途任务并清理短期上下文。
- 公开使用时应提供明确的 AI 内容标识，不能把模拟互动作为真人互动证据。
- 输出必须经过基础内容检查；具体过滤实现需要独立验证，不能只依赖 Prompt。

## 9. 跨平台要求

- Windows 和 macOS 都属于正式目标平台，不把其中一个描述为未来附加项。
- 屏幕录制、麦克风、置顶窗口、点击穿透、托盘和快捷键需要分别在两个平台实测。
- 当操作系统权限被拒绝时，应用要解释缺少哪项权限以及如何恢复。
- 平台能力不一致时，可以采用不同实现，但用户可见语义应保持一致。
- 未通过实测的系统版本、独占全屏或多显示器能力不得提前承诺。

## 10. MVP 验收

MVP 通过需要提供真实的端到端证据，而不只是静态界面或预置弹幕：

1. Windows 和 macOS 上各完成一次从启动到停止的会话。
2. 真实屏幕变化能够影响随后生成的弹幕。
3. 用户说出一段话后，ASR 文本能够影响随后生成的弹幕。
4. 用户发送一条文字弹幕后，至少一个相关观众能够结合该消息继续交流。
5. 用户用文字或语音点名同一观众两次时，回应保持身份、人格和近期对话连续性。
6. 不同观众对同一内容能够表现出可识别的偏好和立场差异。
7. 六个内置模式和当前 32 个 PersonaTemplate 可用，模式能够按 viewer count 和权重确定性创建 1 到 32 个 ViewerInstance。
8. 复制模式后编辑其人格，其他模式和内置基线保持不变；版本不兼容的 `personality.md` 被明确拒绝。
9. 导演产生 `MemeCandidate` 时候选不会直接出现在 Overlay；确认入库后只进入当前模式，并可撤销。
10. 重启应用后，PersonaTemplate、RoomLongTermMemory 和模式梗库仍然属于正确 Room 或模式。
11. 用户删除某条 Room 记忆后，后续 Viewer 请求不再包含被删除内容。
12. 外部模型不可用时，应用明确提示错误且仍能停止会话。
13. 弹幕层不会阻止用户操作目标应用，并存在可靠的恢复入口。
14. 暂停期间不产生需要恢复后补发的旧弹幕。
15. 停止后麦克风和屏幕采集结束，在途模型任务被取消或失效。
16. 日志和界面中不泄露模型凭据。

延迟、资源占用、采样频率和支持的模型列表需要记录实测结果，但当前不设置未经验证的硬数字。

## 11. 产品开放问题

- MVP 是优先同时保证 Windows/macOS，还是先在一端完成闭环后立即补齐另一端？
- 首次体验是要求用户填写模型配置，还是提供一个可选的默认 Provider？
- 首次进入时默认激活六个内置模式中的哪一个？
- 是否需要用基于真实使用数据的衰减评分替换当前 30 天低频归档规则？
- 是否需要采集系统音频，还是屏幕画面与主播麦克风已经足够？
- 公开录制时，AI 标识应显示在控制台、弹幕层还是两者同时显示？
